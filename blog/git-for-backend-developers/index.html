Git for Backend Developers: Commits, Branching, Rebasing and Recovering from Mistakes

Write commits a reviewer can follow, choose between merge and rebase, resolve conflicts with confidence, and recover from almost any mistake.

On this page

    Introduction

    Most developers learn enough Git to commit, push and pull, then hit a wall the first time a rebase goes wrong or a commit seems to vanish. On a backend team, that wall costs real time: a messy history slows down code review, a bad merge breaks a deploy, and a committed secret has to be rotated everywhere.

    This guide covers the Git that matters in day-to-day backend work:

    • How Git stores your work, in just enough detail to stop it feeling like magic
    • Writing commits and branches a reviewer can follow
    • Merge vs rebase, and cleaning up history before a pull request
    • Resolving conflicts and undoing almost any mistake
    • Finding the commit that broke something, and keeping secrets out of the repository

    Every command and output below was run on Git 2.43 in a scratch repository. Commit hashes will differ on your machine.

    How Git Works in Five Minutes

    A few ideas explain almost every Git command:

    • A commit is a snapshot of the whole project, plus a message, an author and a pointer to its parent commit. Git stores snapshots, not diffs; diffs are computed when you ask for them.
    • A commit's ID is a hash of its content and its parent. Change anything, even the message, and you get a new commit with a new ID. That is why rebasing and amending "rewrite history".
    • A branch is a movable pointer to one commit. Creating a branch costs almost nothing. HEAD points to the branch you are on.
    • Your work moves through three areas: the working directory (files on disk), the staging area or index (what the next commit will contain), and the repository (committed history).
    working directory  ──git add──▶  staging area  ──git commit──▶  repository
        ◀──git restore──                ◀──git restore --staged──

    Keep these in mind and commands stop being incantations. git reset moves a branch pointer. git rebase copies commits onto a new parent. A "lost" commit is usually still in the repository, just no longer pointed to by any branch.

    A Sensible Setup

    A few settings remove common friction. All of these exist in current Git releases:

    git config --global init.defaultBranch main
git config --global pull.rebase true            # rebase local commits on pull instead of merging
git config --global fetch.prune true            # remove branches deleted on the remote
git config --global push.autoSetupRemote true   # first push of a new branch sets its upstream
git config --global rebase.autoSquash true      # apply fixup! commits automatically (see below)
git config --global rebase.updateRefs true      # keep stacked branches in sync during a rebase
git config --global merge.conflictStyle zdiff3  # show the original text in conflicts
git config --global rerere.enabled true         # remember how you resolved a conflict

    Add a global ignore file for editor and OS clutter (.idea/, .vscode/, .DS_Store) so project .gitignore files only list what the project creates, such as __pycache__/, .venv/ and .env.

    Writing Good Commits

    A commit is a unit a reviewer reads, a deploy can roll back, and git bisect can test. That gives three rules:

    • One logical change per commit. A migration, the model change it needs, and its tests belong together. An unrelated formatting fix does not.
    • Every commit should build and pass tests, so you can check out any point in history and trust it.
    • The message explains why. The diff already shows what changed.

    Stage selectively when your working directory holds more than one change. git add -p walks through each hunk and asks whether to include it, so one messy afternoon becomes several clean commits.

    A message format that works on any team:

    Add retry with backoff to payment client

The provider returns 503 during its nightly maintenance window, which
failed about 40 checkouts a night. Retry idempotent calls up to three
times with exponential backoff; non-idempotent calls still fail fast.

Refs: PAY-214
    • A summary line in the imperative mood ("Add", "Fix", not "Added"), around 50 characters and no more than 72.
    • A blank line, then a body that explains the problem and the reasoning, wrapped at about 72 characters.
    • A ticket reference if your team uses one. Some teams also use the Conventional Commits prefixes (feat:, fix:) to generate changelogs.

    Messages like "fix", "wip" or "changes" cost nothing to write and a lot to read six months later, when you are trying to understand why a line exists.

    Branching Strategies

    A branching strategy is a team agreement about where work happens and how it reaches production. Three are common:

    Comparison of common Git branching strategies
    StrategyHow it worksFitsTrade-off
    Trunk-basedShort-lived branches (hours to a couple of days) merge into main; unfinished features hide behind feature flagsTeams that deploy continuously with strong CINeeds good tests and flag discipline
    GitHub FlowBranch from main, open a pull request, review, merge, deploy mainMost web services and small teamsOne production line; no separate release branch
    GitFlowLong-lived main and develop, plus feature, release and hotfix branchesVersioned releases, several supported versions, QA gatesMore branches, more merges, slower feedback

    For a typical backend service that deploys often, GitHub Flow or trunk-based development keeps things simple. GitFlow earns its overhead when you ship versioned releases or must maintain several at once. Its author added a note in 2020 recommending simpler workflows for continuously delivered software.

    Whatever the strategy, a few rules hold:

    • Name branches by type and purpose, such as feature/PAY-214-payment-retry or bugfix/order-total-rounding
    • Keep branches short-lived; the longer a branch lives, the worse its merge
    • Protect main: require pull requests, reviews and passing CI
    • Delete branches after merging

    Merge vs Rebase

    Your feature branch has two commits. Meanwhile someone pushed "Fix settings" to main. You can bring that change into your branch two ways.

    Merge creates a new commit with two parents. Nothing existing changes:

    *   Merge branch 'main' into merge-demo
|\
| * Fix settings
* | Test orders endpoint
* | Add orders endpoint
|/
* Add app

    Rebase replays your commits on top of the new main, as if you had started there. History becomes a straight line, but your two commits are new copies with new IDs:

    * Test orders endpoint
* Add orders endpoint
* Fix settings
* Add app
    git switch feature/orders
git fetch origin
git rebase origin/main          # or: git merge origin/main

    Both are correct. Rebase gives a readable, linear history and makes git bisect simpler. Merge preserves exactly what happened and never rewrites commits. A common team choice is: rebase your own branch to stay current, then merge it into main through the pull request.

    The one rule of rebasing

    Do not rebase commits that other people have based work on, such as main or a shared branch. Rebasing your own feature branch is fine. When you must update a pushed branch after a rebase, use git push --force-with-lease, which refuses to overwrite commits on the remote that you have not seen. A plain --force silently discards them. If your editor or IDE fetches in the background, add --force-if-includes too; otherwise a fetch can make the lease pass for commits you never actually looked at.

    Merge strategies for pull requests

    • Merge commit: keeps every branch commit plus a merge commit. Full history, noisier log.
    • Squash and merge: turns the whole branch into one commit on main. Clean, and one commit per pull request makes reverting easy. You lose the individual commits.
    • Rebase and merge: replays each commit onto main with no merge commit. Linear, but every commit must stand on its own.

    Squash suits teams whose branch commits are messy. If your commits are already clean and meaningful, a merge commit or rebase keeps more useful history.

    Cleaning Up History Before a Pull Request

    Review comments usually lead to small fixes for earlier commits. Instead of a trail of "address review" commits, attach each fix to the commit it belongs to. git commit --fixup marks it:

    git add models.py
git commit --fixup=<sha-of-"Add order model">
git rebase -i --autosquash origin/main

    The rebase moves each fixup! commit under its target and folds it in:

    Before                         After
fixup! Add order model         Add order view
Add order view                 Add order serializer
Add order serializer           Add order model
Add order model

    Interactive rebase (git rebase -i) can also reorder, reword, split or drop commits. Use it on your own branch before review, never on commits others already have.

    For the latest commit only, git commit --amend adds staged changes to it or edits its message.

    Resolving Conflicts

    A conflict happens when both sides changed the same lines. Here main lowered a timeout to 10 while a feature branch raised it to 60. With the default style, Git shows only the two new versions. With merge.conflictStyle zdiff3, it also shows the original:

    <<<<<<< HEAD
TIMEOUT = 10
||||||| af76355
TIMEOUT = 30
=======
TIMEOUT = 60
>>>>>>> feature/timeout
RETRIES = 3

    Seeing that the original was 30 tells you both sides deliberately changed it in opposite directions. That is a conversation with the other developer, not a coin toss. Without the middle section, you would only see two numbers.

    To resolve:

    1. Edit the file to the correct final content and remove the markers.
    2. Run the tests. A clean textual merge can still be a broken program.
    3. git add the file, then git commit for a merge or git rebase --continue for a rebase.

    If it goes badly, git merge --abort or git rebase --abort returns you to where you started. With rerere.enabled, Git records each resolution and reapplies it if the same conflict appears again, which helps when you rebase a long branch several times.

    Undoing Mistakes

    Almost everything in Git can be undone. Pick the command by where the mistake is:

    Which Git command undoes which mistake
    SituationCommandEffect
    Discard uncommitted changes to a filegit restore app.pyFile matches the last commit. The changes are gone.
    Unstage a file, keep the changesgit restore --staged app.pyRemoved from the next commit only
    Fix the last commit's message or contentsgit commit --amendReplaces the last commit
    Undo local commits, keep changes stagedgit reset --soft HEAD~1Branch moves back; files untouched
    Undo local commits, keep changes unstagedgit reset HEAD~1The default --mixed mode
    Throw away local commits and changesgit reset --hard HEAD~1Branch and files move back
    Undo a commit that is already pushedgit revert <sha>New commit that reverses it; history is not rewritten

    The line that matters most: rewrite only local history; revert shared history. reset and --amend change commit IDs, which breaks everyone who already pulled them. revert adds a new commit, so it is safe on main:

    Revert "Round tax to two decimals"
Round tax to two decimals
Add tax calculation

    Recovering "lost" commits with the reflog

    Git records every position HEAD has been in, in the reflog. Here three commits were made, then git reset --hard HEAD~2 appeared to delete two of them:

    $ git log --oneline
edb832b Add payment client

$ git reflog -n 4
edb832b HEAD@{0}: reset: moving to HEAD~2
c0a5de0 HEAD@{1}: commit: Add payment webhooks
c4ad21c HEAD@{2}: commit: Add retry to payment client
edb832b HEAD@{3}: commit (initial): Add payment client

$ git reset --hard HEAD@{1}
$ git log --oneline
c0a5de0 Add payment webhooks
c4ad21c Add retry to payment client
edb832b Add payment client

    The commits were never deleted, only unreferenced. The same works after a botched rebase: find the entry before the rebase started and reset to it, or create a branch there with git branch rescue HEAD@{5}. By default, unreachable reflog entries expire after 30 days, so recover soon.

    The reflog cannot recover changes that were never committed or stashed. That is the real danger of git reset --hard and git restore: commit or stash first if in doubt.

    Finding the Bad Commit with git bisect

    A test that passed last week fails today, and 30 commits landed in between. git bisect binary-searches the history: you mark one good and one bad commit, and it checks out the midpoint until it finds the first bad one.

    If a command can tell good from bad, Git runs the whole search for you. Exit code 0 means good, anything else means bad:

    git bisect start HEAD HEAD~30          # bad commit first, then a known good one
git bisect run ./check.sh
git bisect reset                       # return to where you started
    #!/bin/sh
# check.sh
python3 -c "from cart import total; assert total([10, 20, 30]) == 60"
    a8e3c52d796e10faf8c2a953b3ecbfc958981462 is the first bad commit
commit a8e3c52d796e10faf8c2a953b3ecbfc958981462
Author: Riyas A C <dev@example.com>
Date:   Thu Oct 15 10:00:00 2026 +0530

    Refactor cart total

    Git found the bad commit among 30 in 5 test runs. With 1,000 commits it would take about 10. In a real project, the check is usually one test: git bisect run pytest tests/test_cart.py -x. This is where small, buildable commits pay off: bisect points at a 10-line change instead of a 2,000-line one.

    Keeping Secrets Out with Hooks

    A secret committed once lives in history forever, even if a later commit deletes it. Anyone with a clone has it. Prevention is far cheaper than cleanup.

    • Read secrets from the environment and keep local values in .env, listed in .gitignore
    • Commit a .env.example with placeholder values so others know which variables exist
    • Turn on secret scanning and push protection on your Git host
    • Add a pre-commit check that blocks obvious secrets before they are committed

    A Git hook is a script in .git/hooks/ that runs at a point in the workflow; a non-zero exit stops the action. This one blocks staged lines that look like an AWS key, a hard-coded Django SECRET_KEY, or a private key:

    #!/bin/sh
# .git/hooks/pre-commit: block staged lines that look like hard-coded secrets
pattern='AKIA[0-9A-Z]{16}|SECRET_KEY *= *"|PRIVATE KEY-----'

if git diff --cached -U0 | grep -E "^\+.*($pattern)" >/dev/null; then
    echo "pre-commit: possible secret in staged changes, commit blocked" >&2
    exit 1
fi
    $ git commit -m "Add settings"          # SECRET_KEY = "django-insecure-abc123"
pre-commit: possible secret in staged changes, commit blocked

$ git commit -m "Add settings"          # SECRET_KEY = os.environ["SECRET_KEY"]
[main (root-commit) 43ae2e8] Add settings
 1 file changed, 1 insertion(+)

    Hooks in .git/hooks/ are not shared through the repository, and anyone can skip them with --no-verify. For a team, use the pre-commit framework with a committed config and a maintained secret scanner such as Gitleaks or detect-secrets, and run the same checks in CI, where they cannot be skipped.

    If a secret does reach a remote, rotate it immediately. Rewriting history afterwards is cleanup, not a fix: the value may already be in clones, forks, CI logs and caches. My post on API fundamentals covers where secrets should live instead.

    Everyday Commands Worth Knowing

    • git stash push -m "wip: refunds" shelves uncommitted changes so you can switch branches; git stash pop brings them back. Name your stashes; anonymous ones pile up.
    • git worktree add ../hotfix main checks out a second branch in another folder. Fix production without stashing or disturbing your current work.
    • git log -S "calculate_tax" finds commits that added or removed a string. Ideal for "when did this function disappear?"
    • git blame -w -C app.py shows who last changed each line, ignoring whitespace changes and following code moved between files.
    • git switch and git restore split the old overloaded git checkout into "change branch" and "restore files". They are harder to misuse.
    • git log --oneline --graph --all draws the branch structure in the terminal. Worth an alias.

    Common Git Mistakes

    • Force-pushing a shared branch, or using --force instead of --force-with-lease on your own.
    • Rebasing commits others have pulled. Their history and yours diverge, and the same changes appear twice.
    • Huge commits mixing unrelated changes, which are hard to review, revert or bisect.
    • Long-lived branches that drift for weeks and end in a painful merge.
    • Committing generated files, virtual environments or .env. Set up .gitignore on day one.
    • Resolving conflicts without running tests, which hides broken merges until CI or production.
    • git reset --hard with uncommitted work, the one loss the reflog cannot undo.

    Conclusion

    Git rewards a small mental model: commits are snapshots, branches are pointers, and history is only lost when nothing points to it and the reflog expires. With that, the rules follow. Make small commits with messages that explain why. Rebase your own work, merge shared work, and revert rather than rewrite anything already pushed. When something breaks, bisect finds it. When something seems lost, the reflog almost always has it.

    Try this today

    Apply the setup block above, then run git reflog in a project you work on. Seeing every position your branch has been in makes risky commands far less scary.

    Frequently Asked Questions

    What is the difference between git merge and git rebase?

    Merge joins two branches with a new merge commit and leaves existing commits unchanged. Rebase replays your commits on top of another branch, producing a linear history with new commit IDs. Rebase your own unshared branches; merge shared ones.

    How do I undo a pushed commit?

    Use git revert <sha>. It creates a new commit that reverses the change, so nobody else's history breaks. Avoid git reset plus a force-push on shared branches.

    Can I recover a commit after git reset --hard?

    Usually, yes. Run git reflog, find the commit, and git reset --hard to it or create a branch there. Unreachable entries expire after 30 days by default. Uncommitted changes discarded by the reset cannot be recovered this way.

    When is force-pushing safe?

    On your own branch that nobody else has based work on, after a rebase or amend. Use git push --force-with-lease so the push fails if someone else pushed in the meantime. Never force-push main or other shared branches.

    Which branching strategy should a backend team use?

    For services that deploy continuously, GitHub Flow or trunk-based development: short-lived branches merged into main after review and CI. Use GitFlow when you ship versioned releases or support several versions at once.
